# Penguins GUI integration protocol

## Status

This document defines the proposed contract between `penguins-gui` and the
independent command-line programs Penguins' Eggs and Krill.

The JSON interface described here is a design proposal. Unless explicitly
marked as current behaviour, command names and options in this document are
not implemented yet.

## Goal

The GUI must orchestrate the tools through stable public interfaces without
importing their internal code:

- Eggs remasters the running system into an ISO;
- Krill installs a live system;
- the GUI validates user choices, starts the selected tool and renders its
  progress and result.

Note: Penguins Tailor is explicitly excluded from the GUI integration protocol.
Tailor is designed to operate on naked (headless/CLI-only) systems to configure
and install desktop environments before any GUI is available; hence, it remains
exclusively a CLI/TUI tool.

Each tool remains useful, installable and releasable without the GUI. The GUI
must also remain usable when only some of the tools are installed.

## Current integration

The first version of `penguins-gui` invokes the existing Eggs CLI:

| GUI action | Current invocation |
| --- | --- |
| Detect Eggs | `eggs version` |
| Standard live ISO | `eggs remaster --path <directory>` |
| System clone | `eggs remaster --clone --path <directory>` |
| Encrypted clone | `eggs remaster --crypted --path <directory>` |

Standard and clone modes run through `pkexec`; stdout and stderr are displayed
as a log after removing ANSI escape sequences. Encrypted mode is opened in a
terminal because Eggs currently needs interactive input. The GUI finds the
result by looking for a recently created ISO in the working directory.

This compatibility layer is intentionally temporary. Human-readable output is
not a reliable API, and directory scanning cannot identify an artifact with
certainty.

## Protocol overview

The proposed protocol has four parts:

1. **capabilities**: the tool describes its version, operations and supported
   options;
2. **inspection**: the GUI obtains system state and selectable data as JSON;
3. **request**: the GUI sends one validated JSON document describing the
   operation;
4. **events**: the tool writes one JSON object per line (NDJSON) until it emits
   a final result or error.

JSON is used for finite responses and requests. NDJSON is used for long-running
operations so that events can be decoded as soon as they are written.

### Proposed command shape

The exact spelling can be adapted to each existing CLI, but all tools should
offer equivalent behaviour:

```text
<tool> capabilities --json
<tool> <operation> --check --request <file> --json
<tool> <operation> --request <file> --events ndjson
```

Reading a request from standard input should also be supported:

```text
<tool> <operation> --request - --events ndjson
```

Standard input avoids temporary files and should be preferred by the GUI. It
is not used when the operation itself requires interactive input.

When JSON or NDJSON output is requested:

- stdout contains protocol documents only;
- every NDJSON event occupies exactly one line;
- diagnostics that cannot be represented by the protocol go to stderr;
- the process exit code remains authoritative;
- output is flushed after every event.

## Versioning

Every document contains a protocol identifier:

```json
{
  "protocol": "penguins/v1"
}
```

Additive fields are allowed within a protocol version and must be ignored by
older clients. Removing a field, changing its meaning or changing a field type
requires a new major protocol version.

## Requests

A request has a common envelope and operation-specific `options`:

```json
{
  "protocol": "penguins/v1",
  "request_id": "018f90c4-8f3c-7e45-a8e0-17b82f116b72",
  "tool": "eggs",
  "operation": "remaster",
  "options": {
    "mode": "standard",
    "working_directory": "/home/eggs",
    "compression": {
      "algorithm": "zstd",
      "level": 3
    }
  }
}
```

`request_id` is generated by the caller and copied into every response and
event. Unknown options must cause validation to fail rather than being silently
ignored.

### Eggs request

```json
{
  "protocol": "penguins/v1",
  "request_id": "018f90c4-a050-7201-96ae-60d119517f78",
  "tool": "eggs",
  "operation": "remaster",
  "options": {
    "mode": "crypted",
    "working_directory": "/home/eggs",
    "compression": {
      "algorithm": "zstd",
      "level": 5
    }
  }
}
```

Allowed remaster modes are `standard`, `clone` and `crypted`, subject to the
capabilities reported by the installed Eggs version.

Passwords, passphrases and keys must never be stored in this document. A secret
must be obtained through a protected interactive channel or file descriptor,
with the request containing only a reference to that channel.

### Krill request

Krill is included in the common design, but integration should begin only when
it is an independent program with a stable public interface.

```json
{
  "protocol": "penguins/v1",
  "request_id": "018f90c4-a619-7f05-90f2-00229a3e622f",
  "tool": "krill",
  "operation": "install",
  "options": {
    "plan_id": "plan-20260922-01",
    "confirmation": true
  }
}
```

An installation request should refer to a previously validated plan rather
than repeating unchecked disk and partition parameters. Destructive operations
always require an explicit user confirmation in the GUI; an AI component may
explain or prepare a plan but must not confirm it.

## Events

All events share a common envelope:

```json
{
  "protocol": "penguins/v1",
  "type": "event",
  "request_id": "018f90c4-a050-7201-96ae-60d119517f78",
  "run_id": "018f90c6-0f3e-75c9-98f2-26766ab66563",
  "sequence": 12,
  "timestamp": "2026-09-22T05:41:13Z",
  "tool": "eggs",
  "tool_version": "26.9.16-10",
  "operation": "remaster",
  "state": "running",
  "step": {
    "id": "mksquashfs",
    "index": 4,
    "total": 7
  },
  "progress": {
    "current": 63,
    "total": 100,
    "unit": "percent"
  },
  "message": "Creating the compressed filesystem"
}
```

This supersedes the smaller event sketches used during the initial design:

```json
{"tool":"eggs","operation":"remaster","step":"mksquashfs","state":"running","progress":63,"message":"Creating compressed filesystem"}
```

The compact forms explain the idea, while the versioned envelope gives the GUI
enough information to correlate simultaneous operations and evolve safely.

### States

The common states are:

| State | Meaning |
| --- | --- |
| `pending` | Accepted but not started |
| `running` | Work is in progress |
| `waiting_for_input` | The tool needs an explicit user action |
| `succeeded` | Finished successfully |
| `failed` | Finished with an error |
| `cancelled` | Stopped on request |

`state` describes the entire operation. A step can include its own state when
needed. `message` is for people and may be localized; program logic must use
stable identifiers such as `step.id` and `error.code`.

### Successful result

The last stdout document of a successful execution is a result. Eggs must
return the exact ISO rather than requiring the GUI to infer it:

```json
{
  "protocol": "penguins/v1",
  "type": "result",
  "request_id": "018f90c4-a050-7201-96ae-60d119517f78",
  "run_id": "018f90c6-0f3e-75c9-98f2-26766ab66563",
  "sequence": 28,
  "timestamp": "2026-09-22T05:59:02Z",
  "tool": "eggs",
  "tool_version": "26.9.16-10",
  "operation": "remaster",
  "state": "succeeded",
  "message": "ISO created",
  "artifacts": [
    {
      "kind": "iso",
      "path": "/home/eggs/egg-of-debian-trixie-colibri-amd64.iso",
      "size_bytes": 1825361100,
      "sha256": "0123456789abcdef0123456789abcdef0123456789abcdef0123456789abcdef"
    }
  ]
}
```

An artifact path must be absolute. Checksums may be omitted when they were not
requested or would add unacceptable work, but the path, kind and size should be
present.

### Error result

```json
{
  "protocol": "penguins/v1",
  "type": "error",
  "request_id": "018f90c4-a050-7201-96ae-60d119517f78",
  "run_id": "018f90c6-0f3e-75c9-98f2-26766ab66563",
  "sequence": 9,
  "timestamp": "2026-09-22T05:43:31Z",
  "tool": "eggs",
  "tool_version": "26.9.16-10",
  "operation": "remaster",
  "state": "failed",
  "message": "Not enough free space",
  "error": {
    "code": "INSUFFICIENT_SPACE",
    "recoverable": true,
    "details": {
      "required_bytes": 6000000000,
      "available_bytes": 4200000000
    }
  }
}
```

Error codes are stable and machine-readable. The message and details help the
GUI explain the problem but do not replace a non-zero exit code.

## Capability discovery

The GUI must not assume that an installed version supports every option. A
proposed `capabilities --json` response is:

```json
{
  "protocol": "penguins/v1",
  "type": "capabilities",
  "tool": "eggs",
  "tool_version": "26.9.16-10",
  "operations": {
    "remaster": {
      "modes": ["standard", "clone", "crypted"],
      "compression": {
        "algorithms": ["zstd", "xz"],
        "level": {"minimum": 1, "maximum": 19}
      },
      "supports_check": true,
      "supports_events": true,
      "requires_privilege": true
    }
  }
}
```

The GUI uses this response to enable controls, not to guess support from a
version string. A missing tool or operation is shown as unavailable without
preventing other tools from working.

## Data required from each tool

### Eggs

Eggs should expose:

1. capabilities and version;
2. a system status document: distribution, release, architecture, live-system
   state and whether remaster prerequisites are satisfied;
3. effective remaster configuration, with secret values redacted;
4. a non-destructive remaster check/plan with estimated space requirements;
5. NDJSON progress events with stable step identifiers;
6. a final result containing the exact ISO path and metadata;
7. structured errors and cancellation handling.

The smallest useful first implementation is JSON events for `eggs remaster`
and a final artifact result. That immediately removes log parsing and ISO
directory scanning from the GUI.

### Krill

Once independent, Krill should expose:

1. capabilities and version;
2. safe system and disk inventory;
3. installation modes and their requirements;
4. creation and validation of an immutable installation plan;
5. NDJSON installation progress;
6. a final installation report;
7. structured errors, cancellation limits and reboot requirements.

Disk selection and partition plans need stable identifiers. The GUI must show
the validated plan and require confirmation immediately before installation.

## Validation responses

`--check` performs every safe validation possible without changing the system.
It returns either an error or a plan:

```json
{
  "protocol": "penguins/v1",
  "type": "plan",
  "request_id": "018f90c4-a050-7201-96ae-60d119517f78",
  "tool": "eggs",
  "tool_version": "26.9.16-10",
  "operation": "remaster",
  "valid": true,
  "warnings": [],
  "estimates": {
    "required_bytes": 6000000000,
    "available_bytes": 17179869184
  },
  "normalized_options": {
    "mode": "standard",
    "working_directory": "/home/eggs",
    "compression": {"algorithm": "zstd", "level": 3}
  }
}
```

`normalized_options` tells the GUI what the tool will actually use after
defaults and aliases have been resolved.

## Privileges and security

- The tool, not the GUI, declares whether an operation needs privileges.
- Privilege elevation must be narrow and visible to the user.
- Requests must not permit arbitrary shell fragments.
- Paths and identifiers must be validated by the receiving tool.
- Secrets must not appear in requests, events, logs or process arguments.
- The optional AI adviser can prepare a request and explain warnings, but the
  normal GUI validates and presents it before execution.
- AI output is never itself trusted input: the selected tool remains the final
  authority for validation.

## Cancellation

The GUI first requests a graceful stop using the platform's normal process
signal. A tool that supports cancellation should emit a final `cancelled`
result after leaving the system in a known state. Capabilities should state
whether an operation is cancellable and identify any non-interruptible steps.

## Implementation sequence

1. Add the common envelope and NDJSON writer to Eggs.
2. Add machine-readable remaster checks and the final ISO artifact result.
3. Update `penguins-gui` to prefer the protocol and retain the current CLI
   adapter for older Eggs versions.
4. Reuse the same envelope when Krill becomes an independent application.
5. Publish JSON Schemas and protocol fixtures so all projects can test the
   contract without invoking privileged operations.

This order delivers immediate value to the working remaster GUI while keeping
Eggs, Krill and `penguins-gui` small and independently maintainable.
